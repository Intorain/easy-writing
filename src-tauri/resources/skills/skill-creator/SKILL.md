## 用途
通过对话把作者的需求整理成可复用技能，交付能查看、继续修改并保存的完整文件候选。

## 先弄清真正要复用什么
只补问会改变实现的缺失信息，例如要处理什么输入、期望什么结果、哪些内容不能改。已有具体例子足够时直接起草，不把创建技能变成固定问卷。
作者说的是修改已有技能时，先用 list_skills 找到对应编号，再 read_skill 读取当前文件。不要凭聊天回忆重写，也不要把作者没要求的改动扩大到其他技能。

## 选择合适的形式
把判断标准、写作方法和取舍写进说明；反复使用的确定性计算、统计、文本转换适合脚本。不要为了显得完整给每个技能配脚本。
说明只保留能改变 Agent 决策的内容。名称与用途让技能容易选对，正文说明目标、必要条件和有用的方法；具体流程只在顺序确实影响正确性时规定。作者的当前要求优先，不能把某个例子变成所有作品的强制套路。
写作方法声明 kind=method，明确替换 chapter-writing、short-story 或作为辅助方法；检查类用 check，平台操作与脚本流程用 tool。不要同时让多个技能争夺同一项决定。
文风与表达参考声明 kind=style，不填写 replaces。它与主写作方法分别选择，随后共同进入任务规则集。分析依据、来源和长篇参考资料可保存在 references/ 下，Agent 通过技能目录按需读取；生成正文必须遵守的内容仍写齐在 instructions 中。

## 脚本约定
脚本位于 scripts/ 下，用 Python 从标准输入读取 JSON，向标准输出返回结果 JSON；错误写到标准错误并以非零码退出。脚本输入输出字段、用途及调用时机写清楚，调用 run_skill_script 时使用实际技能编号及 scripts/ 内的相对路径。
优先使用标准库。第三方依赖列在 requirements.txt，不在代码里安装。脚本只拿到显式传入的数据，没有默认注入的作品库；需要作品内容时由 Agent 先读取，再作为输入传给脚本。不要编造已有工具或硬编码作者的本机路径。
脚本是本地用户权限代码，不是沙箱。候选不能运行，也不能声称已验证；安装后仍按平台状态准备环境、安装依赖和确认当前脚本版本。除非确有脚本执行结果，不把“已生成”说成“运行通过”。

## 在平台上怎么做
用 prepare_skill 提交完整说明和文件，成果面板会显示可编辑的技能候选。创建候选不会安装技能，也不会执行脚本。向作者说明技能解决什么、是否包含脚本，以及尚未验证的部分。
继续讨论时用 read_artifact 读取最新候选，带 artifact_id 和 expected_revision 更新同一份候选。作者可能在面板里改过文件，不能用旧内容覆盖。files 是完整文件集合，保留没要求删除的文件。
修改已安装技能时，候选绑定 read_skill 返回的技能编号和文件版本；内置技能保存为作者副本。作者在成果面板点击“保存技能”后才安装或更新，脚本运行确认与保存分开。
