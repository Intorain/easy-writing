# Agent 开发约定

易创 Agent 的行为由五层共同决定。每一层只管自己该管的事；行为出问题时，先找到是哪一层，在那一层改。

| 层 | 放什么 | 在哪里 |
|---|---|---|
| 宿主硬约束 | 权限、写入授权、数据完整性、成本闸门（联网确认）、契约校验、参考书防串 | `src-tauri/src/agent_*.rs` |
| 系统提示词 | 角色、判断原则（附原因）、硬规则的说明 | `worker.py` 的 `system` |
| 技能 | 某类任务的方法、判断标准、常见坑 | `src-tauri/resources/skills/<id>/SKILL.md` |
| 工具说明与契约 | 工具做什么、参数含义、成本与副作用、返回什么 | `worker.py` 各 `@tool`、`contracts.py` |
| 评测 | 在真实场景下检验判断是否合理 | `tests/*_live.py`（真实模型）、其余测试（假宿主） |

## 1. 该写死的放在宿主，该判断的交给模型

- 模型再聪明也不能自己拿主意的事，写进宿主代码：写入正文要作者授权、保存要核对版本、联网抓取要作者确认、参数按契约校验、参考书人名不能进作者作品、裁决要附作者原话。
- 怎么理解请求、要不要先问、问什么、用不用数据、先做哪步，交给模型判断。不要在代码或提示词里写“遇到 X 就调 Y”。

## 2. 系统提示词：写原则和原因，不写流程

- 分节写：角色、先理解再动手、用数据的代价、硬规则、记忆与上下文、各类任务的共同要求、和作者说话。
- 每条原则说清为什么，比如“联网抓取一类榜单要几分钟，所以……”。模型知道原因，才能在没写到的情况下自己推断。
- 硬规则单独列出，并注明平台也会校验，让模型知道这是底线、不是建议。
- 具体任务的做法（写章、短篇、拆书……）放进技能，不塞进系统提示词。
- 不为修一个现象加一句补丁。补丁句会互相牵制：修好了“问太多”，就冒出“该问不问”。

## 3. 技能：写知识和标准，不写死路线

- `description` 写清两件事：做什么，什么时候用。模型只看描述决定要不要读全文。
- 正文写目标、要先弄清的信息及原因、可选的做法与取舍、好结果的标准、常见坑。
- 只有容易出错、需要逐步校验的多步操作（比如写入前的核对）才写成步骤清单。
- 不和系统提示词、工具说明重复；要引用工具就写清它适合什么场景。
- 正文要有 `## 用途` 一节（宿主的技能校验会检查）。改了技能内容要升 `version`，作者改过的副本会收到新版提示。
- 写作方法类技能（`kind: method`，如章节写作、短篇写作）有两类读者：规划的 Agent 读全文；宿主把正文展开进任务规则集，
  交给写作模型和读者评审。所以工具步骤、什么时候问作者，写在 `## 在平台上怎么做`、`## 什么时候问作者` 两节里，
  展开规则集时这两节会被去掉（`agent_ruleset::method_text`），写作模型只拿到写法本身。
- 技能要用的数据如果没有工具能取到，就补一个只讲事实的工具，不让模型去猜。
- 文风技能用 `kind: style`，与主方法分开选择；`resolve_ruleset(style_skill_id=...)` 固定本次使用，`configure_book_writing` 可按作者原话绑定到书。写法随规则集进入生成与编辑评审；盲读阶段不接收写法提示。技能更改或停用后旧候选的写作依据失效。
- `references/` 内的文本资料随技能进入虚拟文件系统，按需读取；技能正文必须包含正文生成所需的全部指引，参考文件承载分析依据与覆盖记录。

## 4. 工具说明：只讲事实

- 写：它做什么、每个参数是什么意思、要花多少时间或额度、有什么副作用、返回什么、失败意味着什么。
- 不写对作者的沟通策略，比如“不要反问作者”“直接调用”。这类话会被模型推广到本不适用的场景。
- 内部结构化输出统一走 `structured_output.py`：SDK 接收由领域类型生成的 JSON Schema，结果仍按同一契约校验；不要把带 Required/Annotated 的 TypedDict 直接交给 SDK 转换。
- 参数要不容易被猜错：必填项应当能从作者的话里得到；是作者给的范围还是默认值，在参数描述里说清。
- 需要作者拍板的高成本、不可逆动作，由工具自己发起确认（宿主生成问题与选项、核对点选），不靠模型自觉。

### 工具分组披露（2026-10-13）

工具有八十多个，参数定义就有几万字符；每次模型调用都带全部定义，又慢又贵。`toolsets.py` 把工具分成常用组与八个领域组（榜单、开书、写作、卷章、故事状态、拆书、技能、灵感）：每次调用只发常用工具、框架自带工具和模型已打开的组；模型要用某组时先调 `open_toolset`，打开状态存在会话状态里，跨轮保留。分组是静态表，不按作者措辞猜。

新增工具时必须归进常用组或某一个领域组（`test_toolsets.py` 会拦）；只在进程内起作用、不经宿主的工具放进 `worker.LOCAL_TOOLS`，不进宿主契约。

## 5. 人在回路

- 需要作者决定时用 `ask_author`：单选、多选、分步问答（steps）、表单、并排对比、确认。问题和选项由模型按这本书的情况给，界面只负责渲染。
- 并行的工具可能同时发起多个确认，宿主等作者全部答完再按中断编号一起恢复。
- 输入入口显式区分 `message`（主输入框的新消息）、`answer`（指定卡片的结构化作答）、`continue`（暂停后继续原任务）。主输入框不能隐式成为某张卡的表单答案。新消息结束旧问题等待，保留对话与成果；旧卡标记 superseded，不伪造选择，也不继承其授权。
- 新消息使用新的图输入，先补齐尚无返回的工具消息，再从规划入口处理；不要用 `Command(resume=...)` 把改口塞给旧工具。并行工具可能已产生结果，以平台当前数据及回执为准，不回滚或重放已完成操作。新的普通对话暂停并脱离等待中的批量任务，不能把该对话完成当成批量章节交付。
- 成果面板的方向选择提交成果编号、版本和项序号，宿主核验后把具体方向交给 Agent。它与主输入框走同一新消息路径，不强迫回答另一张卡，也不覆盖尚未发送的输入草稿。
- 提问选项要代表可以直接作答的具体内容。提问只由主 Agent 通过 ask_author 发起，不用第二个模型把普通回复改写成新的中断。必答/选填提示由界面根据字段生成，不依赖模型在问句中自行描述提交规则。

## 6. 用评测驱动，而不是加规则

1. 发现行为问题，先把那句真实的话写成评测用例，复现问题。
2. 判断是哪一层导致的：原则缺失？技能误导？工具说明有歧义？参数设计让模型只能猜？
3. 在那一层改，跑评测；同时看其他用例有没有被带坏。
4. 评测按结果判分（调了哪些工具、参数是什么、有没有问作者、有没有越权写入），不比对回复措辞。指定书籍或章节的任务还要核对目标编号、成果关联、实际版本变化与成功结果，不能只检查工具名字。
5. SDK 适配用真实 SDK + 本地 HTTP 传输夹具验证构造、序列化、解析与校验；不要用替身的 `with_structured_output` 代替这项检查。行为评测的假宿主也要区分不同章节，保留候选与版本，拒绝无效引用。

评测放在 `tests/test_<模块>_live.py`，共用 `tests/live_harness.py`：它按宿主的方式加载内置技能，
用假宿主记录调用（`host.names()`、`host.args_of(...)`、`host.formal_writes()`、`host.online()`），
`run(...)` 返回（宿主，作者被问到的引导卡，文字回复）。注意假宿主看到的是工具调宿主时用的名字，
比如起草正文是 `draft_begin`、写短篇是 `short_begin`。

新写或改过的评测，先用按剧本出招的假模型演练一遍：“做对”的剧本要判通过，“做错”的剧本要判失败，
确认评测本身判得对，再拿去衡量真实模型。写剧本时注意：起草正文（draft_chapter、draft_short_story）会让写作模型再取一条回复作正文；
check_chapter 会让读者评审再取一条结构化回复；revise_spans 用结构化输出；工具参数要符合契约，否则在参数边界就被拦下、到不了宿主。

真实模型评测默认跳过，配置模型后运行：

```
EW_AGENT_LIVE_MODEL='{"modelCode":"...","baseUrl":"...","apiKey":"..."}' pytest tests/*_live.py
```

改了系统提示词、技能或工具说明之后，至少跑一遍改动涉及的模块和选题模块。

## 8. 技能文件管理

- `agent_skill_files.rs` 统一处理技能编辑、目录导入、导出与旧记录迁移。内容以技能文件夹为准，数据库中的说明是供 Agent 查询的索引；启停、脚本确认和运行回执是数据库元数据。
- 人工编辑与 AI 创建都提交同一个 `AgentSkillDraft`，保存前校验路径、大小和读取版本。前端和模型不能指定保存目录、来源或运行授权；内置技能编辑保存为新副本，旧记录迁移保留身份。
- AI 创建走现有对话 Agent，方法在 `skill-creator/SKILL.md`；`list_skills` / `read_skill` 读取现有技能，`prepare_skill` 创建或更新 `kind: skill` 的会话成果。不要另开一套生成提示词和模型请求。
- `agent_skill_authoring.rs` 绑定候选版本、目标技能与文件版本。作者在成果面板编辑后，继续发送对话前先保存候选；`skill_adopt` 只对界面开放，复用文件服务保存，模型不能借候选获得运行授权。
- 生成、查看、保存均不执行脚本或安装依赖。脚本与依赖变化后必须重新确认，依赖安装也校验确认版本。
- 运行复制已确认的技能文件快照；缺文件、缺环境、缺依赖、待确认与运行失败分别报告。文件查看入口始终保留，不与运行确认按钮绑定。
- 文件管理回归在 `agent_skill_files_tests.rs`，执行与环境回归在 `agent_skill_runner_tests.rs`；前端验证覆盖对话入口、成果卡、候选编辑与显式保存，不能把生成候选当作已经安装或授权运行。
- 对话候选回归在 `agent_skill_authoring_tests.rs`，模型行为评测在 `test_skill_authoring_live.py`，先用 `test_skill_authoring.py` 演练正确行为、过期修改和未经采用就运行脚本的判定。


### 发布与技能生命周期约束

- 提示词备份与技能包恢复统一通过 `prompt_files.rs` 的范围；技能编号变更必须同时更新引用和文件路径，恢复不继承脚本授权。
- 脚本确认与卸载使用宿主生成的确认编号，按真实作者点选放行，不接收模型传入的 approved 标记。待确认的版本变化后生成新确认。
- 停止信号必须传递到脚本执行器，不能只终止模型 worker。技能文件变更、运行和卸载共用生命周期锁。
- `pnpm check` 为基础检查，`pnpm check:local` 为完整本地回归；缺失本地测试时不能宣称通过，测试文件不上传远程。


### 对话交付与评审（2026-10-06）

- 明确采用已展示草案的自然语言请求走 `adopt_book_plan`；运行时独立解释真实作者原话，宿主绑定作者消息、展示时的版本、一次性凭据和当前版本。否定、引用、只选设定不算建书授权；不明确时在当前对话确认。界面与对话共用 `agent_book_plan::adopt` 事务。
- `author_interaction.py` 只解释指定草案的采用授权，不生成创作提问。ask_author 的已提交答案在工具返回后作为作者消息进入下一次规划；当前请求完成即结束，后续建议不能自动变成待答任务。
- 记忆按来源类型生成提取契约：只有作者消息允许采用/否决决定，资料与正文由平台固定为摘要。模型选择原文片段编号，由程序复制引文，不依赖模型逐字抄写。来源原文完整传递，按所选模型上下文、Schema 和输出预留分批；失败与延后来源都进入 pendingSources，跨轮保留。旧记忆整条保留或整条省略，不截掉条件。失败重试次数由 `model_limits.py` 的运行边界统一管理。`memoryStatus` 按 author/all 阶段保存进度与脱敏失败原因；成功阶段不能清掉另一阶段的失败。手动重试不运行写作图、不清空未发送的输入草稿。
- `prose_delivery.py` 管理写作交付（2026-10-18 起）：编辑核对一次、有原文依据的具体问题定向修订至多一次、核验改动（原问题解决、事实保留、范围正确）。核验不过就恢复改前稿照常交付；没改成的编辑意见留在报告里作内部记录，不变成作者的活。只有程序核实的阻断（空稿、截断、整段重复、敏感词、与参考书逐字重合）把稿子留在草稿（needs_attention）。ready / awaiting_author 之后，`_submit_delivered` 在稿子挂着章节且写入目标已确定时调用 `save_chapter(automatic=true)` 存成新版本；宿主不放行（目标未定、生成期间正文被改、通道要求确认、阻断）就带回 `saveOutcome`，不发确认卡。独立的 check_chapter 仍只审查；作者指定段落的改稿走 revise_spans（paragraphs / quotes + instruction），整体再过一遍用 polish_draft。reviewComplete 只表示评审完成，不保证真人水平；正文直接显示在对话里，回复不复述。
- 交付预算统一由 model_limits.py 管理，单次运行共享；每次修订预留复评调用，无改善停止、退步通过已校验回执恢复前稿，达到预算如实标记未完成。不以固定修订次数、标点数量或模型分数判定质量，不让 Agent 换操作编号绕过预算。作者编辑、来源变化与规则过期均保护旧版本；显式新任务在新规则下生成关联候选。
- 平台画像、目标读者和作者文风随开书草案保存并采用；已有作品用 configure_book_writing 基于真实作者原话更新。三者进入同一规则集与指纹，生成、修订和评审共同使用。书籍恢复时 book-requirements 与作品编号一起重映射。程序模式检查只给观察，不能靠关键词断言有没有钩子或有没有真人感。
- 修订范围由 `revise_begin` 冻结，`artifact_replace` 校验版本、指纹和允许的段落范围，拒绝越界、重叠和删除整章。引文定位与修订范围分开：宿主用真实原文核对引文，唯一精确匹配可校正模型段号；连续修订块必须含有效引文，允许联动邻段，不机械扩展固定数量的邻段。输出任一越界、重叠都整次拒绝，不能过滤后提交残缺修改；格式校正与复评共用有限调用预算。
- CriticIssue 的 repairMode、repairRanges、fix 为模型输出必填，旧报告仍兼容；缺处理方式或缺有效定位不能标记交付完成。复评拿到前稿、当前稿与真实差异，而非仅根据模型分数判断改善。已完成起草的重放不重新调用写作流覆盖候选。
- 成果按编号读取时统一核对当前会话或关联作品访问范围，同一作品的候选允许跨会话只读；polish_draft 在当前会话建立关联修订副本。读取遗漏 book_id 不会将已可访问候选误报为不存在；缺失或无权访问返回可纠正工具结果，不能让一个错误编号终止整轮。
- 基础检查、读者评审未运行、评审失败必须分开表达，错误保留安全的阶段与原因，不持久化供应商原始响应或凭据。真实模型评测只证明对应案例，不以模型自评声称正文有人类作者水平。

### 运行资源与判断策略

- `model_limits.py` 统一管理模型容量与技术运行边界。上下文、输出上限来自模型管理设置，缺项才采用兼容默认值；各任务不得再通过 `model_copy` 覆盖为自己的固定 token 上限。
- 内部结构化请求统一经过 `invoke_structured`，流式正文经过 `prepare_request`；估算包含输入、结构化 Schema 与输出预留。必要输入超限应报告明确原因，不能截断作者原话、正文或规则后继续执行。
- 超时、重试次数、规划调用上限属于可解释的技术默认值，集中定义；它们不能代替文风、授权和创作完成度判断。规划预算向 Agent 公开，达到硬上限仍由 SDK 阻断。
- 自然语言授权依据真实的前一轮对话、当前完整作者答复和已展示的候选版本。不能把某句话固定标成同意或含糊；解释器只返回语义决定，原话由程序复制，宿主仍核对消息、一次性凭据和版本。
- `model_protocol.py` 统一处理模型工具调用协议：invalid_tool_calls 转成仅可返回错误的调用信封，contract_middleware 在执行前退回原始参数供模型修正，不猜测修补 JSON，不执行该操作。已保存的旧历史缺少这类错误回执时，在发出请求前补齐对应位置，保留原检查点与有效结果，不伪造成功。HTTP 400 是请求格式问题，不显示为网络连接失败。
