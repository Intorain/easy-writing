# 开书流程调研与工具契约整改

日期：2026-09-27。本文把社区资料中的事实、产品判断和本次实现分开记录。

## 调研依据

| 来源 | 可核对的做法 | 对易创的启发 |
|---|---|---|
| [novelWriter 项目文档](https://novelwriter.io/docs/user_interface/projects.html) | 用户可以先创建作品容器，再组织正文与笔记；项目名称可修改，稿件可标注不同完成状态。 | 创建本地容器不代表全书已经定稿。易创“项目”仍是会话组织空间，不能照搬其他软件的同名概念。 |
| [MuMuAINovel 开源使用指南](https://github.com/xiamuceer-j/MuMuAINovel/blob/main/README.md) | 用户主动选择创建向导，输入基本信息，生成大纲和角色，然后编辑完善。 | 快速开书可以成立，但选择生成向导与泛泛地说“帮我写小说”是不同的操作范围。不能把它直接照搬成自动采用所有生成内容。 |
| [番茄：开书不卡壳？大纲这样写才不崩](https://fanqienovel.com/writer/zone/article/7528322925343014936) | 课程按阅读积累、目标定位、核心框架、大纲及作品包装、动笔组织。 | 网文开书要先找定位和故事支撑，不能只选题材、外挂和开局模板。 |
| [番茄：新手如何写一个好故事](https://fanqienovel.com/writer/zone/article/7407742604059623448) | 课程强调题材、灵感、主角身份、主角目标、冲突与对抗。 | 引导优先问目标与阻碍、读者期待等关键缺口，不需要先填满人物百科。 |
| [雪花法原作者说明](https://www.advancedfictionwriting.com/articles/snowflake-method/) | 从小规模故事概括逐步扩展，允许回改，也明确方法并非适合所有作者。 | 支持逐层完善，不能把十步方法变成不可跳过的表单。 |
| [Writing Excuses：混合大纲与探索式写作](https://writingexcuses.com/12-22-hybrid-outlining-and-discovery-writing/) | 作者讨论粗纲、探索角色、试写及随写作调整结构的混合做法。 | 支持先试写再完善；不把“完整大纲”设成开书硬门槛。 |

这些来源没有规定统一的软件审批流程。下面的采用边界是易创作为 AI 代理写入工具的产品判断，而不是声称所有作者都必须这样写。

## 推荐流程

1. **明确创作方向。** 了解题材、预期读者、想提供的阅读体验。已经说明的信息不反复询问。
2. **形成最小故事骨架。** 主角想要什么、受到什么阻碍、核心机制与代价、开篇准备兑现什么。问题随具体故事变化。
3. **整理可编辑的开书草案。** 展示工作书名、已有骨架、阶段主线和未定事项。姓名、最终书名、后期大纲允许留待后续决定。
4. **作者采用当前版本。** 可以只用一个暂定名建立空作品，也可以采用当前构思。由界面动作绑定草案编号和版本；选了题材或开局，不代表采用 AI 后来补出的其他内容。
5. **按下一步指令创作。** 可继续完善、先试写或保存指定章节。采用开书草案不自动触发第一章写入。试写稿保存在会话成果中，不要求先建项目或书籍。

两种推进方式共用这条边界：探索式允许先试写；规划式允许先展开阶段主线。二者都可回改，均不强制全书细纲齐全。原书架的手动建书入口仍可直接创建；Agent 对话默认采用可审阅的协作方式，不把宽泛请求视为全自动委托。

## 当前问题的根因

原工具把人物资料声明为任意 `dict`，而 Rust 层要求年龄为字符串、定位为枚举整数、标签为字符串数组。模型看到的约束和实际接口不一致。校验失败又以普通运行异常冒泡，导致 `age 必须为文本` 出现在用户界面，并让恢复重放同一份错误参数。

因此整改不是对年龄做一次强制转换，也不是给错误文字换个说法。

## 本次实现

- `agent-runtime/contracts.py` 定义严格的字段结构、枚举、列表、可省略项和来源对象。`export_contracts.py` 从实际工具定义导出 `tool-contracts.json`；构建前检查是否同步。
- 模型调用前和 Rust 写入前使用同一份 JSON Schema。年龄仍是年龄描述文本；未知时省略。不把数字、数组或对象随便转成字符串。JSON 中数学意义上的整数（如 `1.0`）在边界统一为整数。
- 新建人物、设定和大纲必须带有效名称；修改已有条目允许只提交改动字段。名称、枚举、标签列表和未知字段都走同一校验边界，不为每种报错增加独立补丁。
- 参数错误返回带字段路径的工具错误消息，交给现有 Agent 循环校正；有限次校正失败才停止，且不执行这次写入。存储故障、版本冲突不伪装成可随便重试的格式问题。
- 写入目标等执行前置条件缺失也返回结构化工具反馈；模型须根据已有作者指令补齐目标选择，不能把引用自动当作写入授权。真实模型复测曾暴露漏选目标导致任务退出，已将这类检查统一到正式写入入口，并验证拒绝时不建卷、不写正文。
- 这遵循 [LangChain 工具参数 schema](https://docs.langchain.com/oss/python/langchain/tools) 和[工具调用中间件](https://docs.langchain.com/oss/python/langchain/middleware/custom)的扩展方式；保留原 LangGraph 检查点和恢复机制，不另外实现一套 Agent 循环。
- 新增 `prepare_book_plan` 保存草案，模型侧 `create_book` 不再直接建立新作品。作者采用的具体版本才通过桌面命令建立或更新作品；创建、构思资料、会话引用和回执在同一事务中提交。
- 旧版已经提前建立的作品不自动删除。根据既有创建回执识别未采用状态，可关联原书重新整理草案，采用时沿用原作品编号。
- 候选、工作书名、未定事项与正式正文保持不同状态。只把当前采用的构思保存到原资料库，后续人物资料与正文按新的作者要求执行。

## 验证要求

- 错误年龄、枚举、列表、编号、空值和未知字段在写入前被拦截；模型收到可校正反馈。
- 重演“错误参数 → 校正 → 成功”，只执行一次有效写入；达到纠错上限时没有部分写入。
- 泛泛提出写书、选择题材、模型伪造 `approved` 字段都不能创建作品。
- 空白或轻量草案允许保存；工作名即可建立作品，不要求完整大纲。
- 作者编辑后，旧版本不能被采用；重复采用不重复建书；存储失败整体回滚。
- 旧版提前创建的空书可沿用，不重复创建，也不偷偷补齐未确认资料。

模型依然可能生成不合法参数；本次的保证是它们不能越过写入边界，并有受限的内部纠错流程。创作质量、存储故障和所有模型供应商的兼容性不能用一组格式测试替代。

## 本轮验证结果

- Python 契约和框架纠错测试 28 项、Rust 回归 66 项、前端与存储回归 196 项通过；类型检查通过。ESLint 无错误，备份测试文件原有的 `any` 警告仍在。
- 前端生产构建、冻结后台打包和最终 Mac 验证包构建通过；验证包未做正式分发签名。
- 真实模型的源码后台和冻结后台均跑通“只生成草案 → 作者采用指定版本 → 新指令保存资料和首章 → 回读与编辑器历史”；冻结后台另通过等待选择/换进程恢复，以及跨会话续写/否决设定两条回归。
- Mac 原生验证应用使用独立数据目录。通过真实页面生成草案、编辑书名、清空大纲、返回讨论、重新打开、采用、打开原编辑器和完整退出后重启。采用前数据库作品数为 0，采用后为 1，正文记录仍为 0；重新打开后的草案保留编辑值和采用状态。空书名时采用按钮禁用。
- 草案更新复用原来的正式构思条目；重复采用、旧版本采用、保存失败回滚、编辑中切换成果面板及备份合并引用均有回归覆盖。
- 本轮没有恢复执行开发客户端原先失败的会话，没有删除或改写其已有书籍。原生验证临时复用的模型配置在验证后从独立验证数据目录清理。

本轮只验证 macOS。Windows、其他模型供应商和正式分发签名未验证；原生窗口验收覆盖本次流程，不代表所有 Agent 界面与生命周期均已验收。
