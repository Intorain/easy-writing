# 桌面存储初始化、迁移与恢复契约

桌面端在启动时选定存储模式，同一运行期间不得切换。统一模式使用已有的 `ew-writing.db`（Tauri `app_config_dir`）和同目录 `assets/`。迁移尚未提交且原数据可读取时，可以继续旧模式：正文仍使用原 SQLite，辅助资料使用 IndexedDB，设置使用 localStorage；仅当 SQLite 没有作品数据且旧 IndexedDB 有正文/目录时，正文也沿用 IndexedDB。提示词文件继续使用 `Documents/易创提示词`。

原生进程保存本次模式，独立 WebView 复用同一个选择。`ew-desktop-storage-startup` 只记录启动偏好，不迁入业务库、不进入备份；数据库完成凭据优先于偏好。网页端沿用浏览器存储。

## 版本与统一清单

`src/storage/migrations/desktop-v1.json` 是前后端共用的迁移定义：任务 ID、来源/目标存储版本、全部旧库/表、设置和封面模块。当前支持存储版本 **0 → 1**，与应用安装包版本号独立。

SQLite `desktop_meta.storage-schema-version` 记录存储版本，`desktop_migrations` 保存迁移任务、状态、原始清单、源校验值、会话编号和恢复副本位置。旧版的 `browser-migration-v1=complete` 是明确支持的历史完成凭据，不能继续作为唯一判定条件。

新增存储格式必须增加明确的版本定义、转换逻辑和兼容验证；不能复用原迁移编号重跑旧库，也不能把未知新版本当成空安装。

## 启动状态判定

检查阶段只读打开既有数据库；数据库不存在时不创建文件。检查 SQLite 完整性、已知表结构、版本标记、迁移记录及新版数据的存在情况。

| 条件 | 行为 | 迁移页 |
| --- | --- | --- |
| 无旧数据、无新版数据、无未完成记录 | 事务写入初始化凭据，直接启动 | 不显示 |
| 存储版本与完整完成记录一致 | 加载设置，直接启动；不再次读取旧库 | 不显示 |
| 存在受支持的历史完成凭据 | 校验结构后补全版本和迁移记录，不重新导入 | 不显示 |
| 完成记录可信，但版本或旧完成标记缺失 | 根据完成记录补全元数据，不重新导入 | 不显示 |
| 无完成凭据，确认存在已识别的旧数据 | 生成迁移计划，保留副本后迁移 | 显示 |
| 上次迁移中断/失败，目标尚未启用，源数据未变化 | 新建会话重试；旧暂存数据随副本保留 | 显示 |
| 完成凭据缺失但已有新版记录/附件引用 | 停止自动处理，不重新灌入旧库 | 显示错误与重试入口 |
| 数据版本较新、记录矛盾、库损坏/不可读 | 停止，不清空、不降级、不创建替代库 | 显示错误与重试入口 |
| 浏览器旧库有未登记的库/表，或已登记的旧表缺失 | 记录提示，保留原数据；继续处理可识别的来源 | 真正迁移时显示处理详情 |
| 数据库缺失，或空库仍残留附件/恢复记录但找不到源数据 | 停止，不能按全新安装处理 | 显示错误与重试入口 |

普通启动与迁移的 UI 模式由协议明确给出，界面不再通过进度名称猜测是否发生迁移。只有计划确认为迁移后才显示迁移进度页。未知源数据库的发现使用平台提供的 `indexedDB.databases()`；不支持该 API 的 WebView 仍严格校验已注册的源数据库、版本和表。

## 迁移提交协议

1. **只读清点**：逐个读取已注册旧数据源；不存在与读取失败是不同结果。旧数据库版本较新或实际读取失败时停止；缺表、未登记的库/表提示后跳过，原数据保留。源记录按确定顺序计算 SHA-256，Blob/字体指纹包含真实字节；缺失或损坏的字体文件连同对应元数据跳过并提示，不阻塞其他资料迁移。
2. **准备计划**：原生端重新核对检查凭据，确认状态未变化。全新安装直接初始化；真正迁移用 `VACUUM INTO` 保存一致性副本，再记录 `running` 会话。只有这一步允许创建迁移任务。
3. **分模块暂存**：每次写入必须携带当前会话编号。模块、数量必须匹配源清单；重复标识和损坏 JSON 被拒绝。写后读回并校验，连空模块也要记录处理完成，避免漏模块误报成功。
4. **提交前复核**：再次只读清点旧数据，并在 SQLite 事务内核对源清单、SQLite 原内容指纹、全部暂存模块及附件哈希。源数据变化、缺项、暂存被修改或会话过期均拒绝提交。
5. **原子启用**：全部业务记录、存储版本、完成凭据在同一 SQLite 事务提交。失败回滚，旧 IndexedDB/localStorage 不删除。已提交后 IPC 回复丢失也不能把任务降级成失败。
6. **失败重试**：原始数据、暂存数据和恢复副本均保留。重试时旧暂存内容先进入新的恢复副本，再创建新会话；过期会话不能继续写入。源数据与失败前不一致时停下来核对，不自动选择覆盖方向。

书籍、正文、历史版本等核心记录同编号但内容不同时，保留现用 SQLite 版本，跳过旧记录并记入迁移凭据的 notes；旧记录继续保留在源库和暂存表。`sync_settings` 同样保留现用 SQLite 值，仅导入缺失项。无法解析的旧记录跳过并记录原因，原来源不删除。新统一资料表中的同键冲突仍中止事务，不混同于上述旧核心记录的兼容处理。

## Agent 分支同步约束（2026-09-26）

本分支已同步主分支的统一存储、迁移、备份恢复及界面改动，同时保留 Agent 页面和编辑器版本校验。

- 迁移与设置加载完成后再导入 `bootstrap.ts`，避免 Pinia、主题或 Agent 页面提前访问未初始化的设置。
- `SqliteWritingStorage` 的版本条件写入、历史快照与备份标记均通过 `trackStorageWrite`；恢复期间不绕过维护锁写库。
- 章节仍使用同一份 `chapter_contents` / `chapter_versions`，这次同步不增加另一份作品库或额外迁移版本。
- 正式 Agent 后台应经平台接口取得模型配置与作品数据。`experiments/agent-runtime` 的 WebKit 配置读取仅属于历史验证程序，不作为统一存储后的业务接口。
- Agent 界面本轮仍为演示状态；同步存储不代表后台业务已接入。

## 备份恢复边界

新 ZIP（格式版本 2）包括数据库一致性快照、业务资料、设置、字体、图片及提示词，校验每个文件的 SHA-256。包内 `idb/`、`local-storage.json` 为兼容历史格式保留名称，不代表桌面实际存储位置。

版本 1 ZIP 和旧目录快照继续可读；不存在于旧包里的工作流、资料无法凭空重建，不会因此清空本机对应资料。未记录目录顺序的旧快照会提示核对，不能推算用户原来的自定义排序。

未完成的恢复通过独立的 `pending-restore` 日志处理：先核对存储版本和状态，再按数据库提交凭据恢复文件或保留新文件，之后重新进行启动判定。恢复流程不等同于旧库迁移。

保留旧库用于数据保护，不代表旧程序能读取升级后的新增数据；不采用长期双写或按时间戳猜测哪份正文应覆盖另一份。

## 验证入口

- `cargo test --manifest-path src-tauri/Cargo.toml --features local-tests --lib`：真实 SQLite/文件系统下的初始化、版本兼容、完成凭据补全、状态异常、会话失效、部分提交、源变化、恢复及回滚。
- `tests/desktop-migration.test.ts`：旧 IndexedDB 保留、空安装、完成后跳过旧库、二次清点、未知数据源和失败重试。
- `tests/startup-migration-visibility.test.ts`：正常启动不显示、真实迁移显示、失败仍有重试入口。
- 前端整体检查：`pnpm check`；资源构建：`pnpm build`。


## Agent 发布候选补充（2026-10-05）

`prompts/skills/<id>/` 的脚本和资源作为完整技能包进出备份，`.venv`、缓存和包替换临时目录不备份。备份、恢复和失败回滚使用同一个文件清单。合并恢复先统一规划 Agent 编号，数据库引用和技能目录使用同一映射；恢复后重新绑定本机路径并清除脚本许可。

旧版只有提示词文档的备份不会清空本机技能包；含不完整技能文件的旧包会明确拒绝恢复技能，避免混用两个版本的脚本与说明。原备份继续保留。

迁移失败页显示本次副本位置，并可选择应用生成的 `before-migration-*.sqlite` 恢复。宿主校验数据库完整性，当前数据库及 WAL 在替换前另存；替换中断按独立日志回滚。工作台已启动后不能走此入口，应使用完整备份恢复。
